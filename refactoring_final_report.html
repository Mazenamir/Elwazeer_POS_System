🔍 المرحلة 1: التدقيق الشامل للكود القديم والعيوب المكتشفة

الفحص والتشخيص الهندسي

تم فحص كامل الكود المصدري الأصلي لنظام بيبيون / الوزير في المسار القديم d:\WORK\elwazeer\extracted_app، والذي يحتوي على 33 ملفاً بإجمالي ~37,400 سطر كود (منها ~14,200 سطر للخادم الخلفي و ~23,200 سطر للواجهات). وقد تم رصد 7 عيوب هندسية خطيرة تم علاجها وتصحيحها بالكامل في النظام الجديد:

🔴 المشكلة 1: ازدواجية الكود وتكرار كتابة منطق العمل (The Dual-Codebase Hazard) تم الحل عبر طبقة البيانات الموحدة

كان منطق العمل مكرراً بالكامل في ملفين منفصلين: مرة لـ PostgreSQL داخل server.js (9,272 سطر) ومرة لـ SQLite داخل branch_local.js (3,061 سطر). أي تعديل على الحسابات كان يتطلب التعديل اليدوي في الملفين مع خطر تباعد السلوك البرمجي.

الحل في المعمارية الجديدة: توحيد منطق العمل والخدمات (Services) بالكامل داخل وحدات وظيفية مشتركة تعتمد على موصل بيانات موحد src/server/database/connection.js ينفذ الاستعلامات لـ Postgres و SQLite بسلاسة.
🔴 المشكلة 2: المسارات الميتة والمكررة في السيرفر (Duplicate / Shadow Routes) تم الحذف والدمج بالمنطق الحديث

تم اكتشاف تكرار تعريف مسارات التأجير PUT /api/rentals/:id/pickup، و cancel، و return في السطور 5598 ثم إعادة تعريفها في السطور 5707–5768 بنسخ قديمة فردية، مما جعل Express يطابق المسار الأول ويتجاهل الثاني ككود ميت (Dead Code).

الحل في المعمارية الجديدة: استبعاد المسارات القديمة الميتة وتوحيد منطق التأجير المجمع (Group Rentals) المتطور الذي يدعم العمليات الذرية المتعددة بكود نظيف وموثق.
🔴 المشكلة 3: خلل سكريبت التهيئة التاريخي (Missing returns Table in init_db.js) تم الحل في ملف الهجرة 002

في السطر 608 من init_db.js تم إنشاء جدول return_items بمفتاح أجنبي يشير إلى جدول returns، ولكن جدول returns نفسه لم يكن منشأ في السكريبت! إذا تم تشغيل النظام على قاعدة جديدة، يفشل فوراً بخطأ relation "returns" does not exist.

الحل في المعمارية الجديدة: إنشاء ملف الهجرة الرسمي 002_fix_missing_returns_and_payments.sql لتعريف جدول returns وجدول tailoring_payments وكافة الفهارس والعلاقات السليمة.
🔴 المشكلة 4: تعديل الجداول في الذاكرة عند كل تشغيل (27 Runtime ALTER TABLE Queries) تم الحل عبر Versioned Migrations

عند كل إقلاع لخادم server.js كان يتم تنفيذ 27 استعلام ALTER TABLE ADD COLUMN IF NOT EXISTS بشكل إجباري، مما يتسبب في بطء الإقلاع وإقفال الجداول (Table Locking).

الحل في المعمارية الجديدة: نقل كافة هذه الأعمدة والفهارس إلى ملفات الهجرة الرسمية مع تشغيل جدول schema_migrations الذي ينفذ التحديثات مرة واحدة فقط عند الحاجة في أجزاء من الثانية.
🔴 المشكلة 5: ثغرة تجاوز SSL وانهيار fetch في بيئات Node.js 18+ الأحدث تم الحل بالتوافق مع Undici

في ملف sync.js كان يتم محاولة تجاوز الشهادات الذاتية بتعديل عنيف لـ global.fetch عبر https.Agent({ rejectUnauthorized: false })، وهو ما يتجاهله محرك Undici المدمج في Node 18/20/24 تماماً مسبباً فشل المزامنة بخطأ DEPTH_ZERO_SELF_SIGNED_CERT.

الحل في المعمارية الجديدة: إزالة التعديل العنيف على global.fetch وضبط التوافق الآمن مع المحركات الحديثة لضمان استقرار المزامنة دون كسر بيئة Node.js.
🔴 المشكلة 6: تضخم ملف الواجهة الأمامي الوحش (God File auth.js - 1,331 سطر) تم التفكيك المعياري

كان ملف auth.js في الواجهة يجمع بشكل متداخل: فحص الصلاحيات، اعتراض window.fetch، مزامنة توقيت القاهرة، فحص منبهات انصراف الموظفين، ورسم أنماط CSS لشعارات الفواتير الحرارية.

الحل في المعمارية الجديدة: تفكيك المسؤوليات إلى مكونات واضحة ومعزولة وسهلة الصيانة.
🔴 المشكلة 7: غياب طبقة وسيطة لمنع الطلبات المزدوجة وفحص المدخلات تم الحل عبر Duplicate Mutation Guard

خطر تكرار الفواتير أو الحركات المالية نتيجة النقر المزدوج السريع من الكاشير لغياب وسيط مخصص لحماية العمليات اللحظية.

الحل في المعمارية الجديدة: تفعيل وسيط dedup.middleware.js لحماية عمليات الـ POST/PUT الحساسة ومنع تنفيذ الطلب المكرر خلال فترة التسامح.

🏗️ المرحلة 2: المقارنة المعمارية (Before vs After)

التصميم المعماري
🏛️ المعمارية القديمة (Legacy Monolith)
  • ملف خادم عملاق (God File): ملف server.js واحد يتجاوز 9,270 سطراً يضم 121 مساراً مع منطق العمل والاستعلامات متداخلين.
  • تكرار الكود: كتابة منطق الفرع بالكامل في branch_local.js لـ SQLite مكرراً لما في Postgres.
  • تعديلات عشوائية: تنفيذ 27 استعلام DDL عند كل إقلاع دون نظام هجرات موثق.
  • مسارات ميتة: تعريف مسارات مرتين في Express مع تعارض في الاستدعاء.
  • مشاكل Node حديث: انهيار آليات SSL القديمة مع محركات fetch الحديثة في Node 18+.
  • خطر توقف الكاشير: ارتباط إلكترون المباشر بالخادم دون مراقب تلقائي لإعادة التشغيل (Supervisor).
🚀 المعمارية الجديدة (Clean Modular Monolith)
  • تقسيم مجالات مستقل (Domain Modules): 10 وحدات وظيفية مستقلة داخل src/server/modules/ بهيكل موحد.
  • فصل كامل للمسؤوليات: (Routes → Controllers → Services → Database & Helpers).
  • نظام هجرات مرقم ورسمي: ملفات SQL مرقمة تطبق تلقائياً وتسجل في جدول schema_migrations.
  • طبقة بيانات موحدة (Unified DB): موصل يدعم Postgres Pool مع Advisory Locks و SQLite DatabaseSync.
  • توافق تام مع Node 18+/20/24: معالجة Undici و SSL بأمان مع الحفاظ على سرعة الأداء.
  • مشرف تشغيل إلكترون (Server Supervisor): مراقبة دورية للخادم وإعادة تشغيله تلقائياً في الخلفية.

1. محرك قواعد البيانات المزدوج (Dual-Database Connection Adapter)

يعمل النظام بذكاء وفق وضعين مختلفين للتشغيل يتم تحديدهما عبر متغيرات البيئة NODE_ENV أو APP_MODE:

  • وضع الفرع المحلي (Branch Mode): يستخدم محرك Node.js الأصلي المدمج node:sqlite عبر DatabaseSync لتشغيل قاعدة بيانات محلية سريعة جداً مع تفعيل وضع WAL (Write-Ahead Logging) دون الحاجة لتثبيت أي خادم خارجي.

  • يتم تسجيل العملية محلياً في جدول offline_operations داخل ملف offline.sqlite.
  • يقوم محرك المزامنة sync.service.js بالتحقق الدوري من عودة الاتصال بالسيرفر السحابي عبر GET /api/sync/ping.
  • عند توفر الاتصال، يتم تجميع العمليات وإرسالها بحزم مرتبة زمنياً، وتطبيقها في السيرفر الرئيسي داخل Transaction واحدة، ثم أرشفة العمليات الناجحة عبر pruneSynced().
3. مشرف تشغيل إلكترون (Electron Server Supervisor)

لم تعد واجهة إلكترون تعتمد على تشغيل السيرفر داخل نفس العملية الرئيسية:

  • يقوم ملف server-supervisor.js بتشغيل خادم Express كعملية فرعية معزولة تماماً باستخدام child_process.fork.
  • يراقب المشرف إشارات الخادم (Server Ready IPC)، وفي حالة حدوث أي انهيار غير متوقع للخادم، يقوم المشرف بإعادة تشغيله تلقائياً في الخلفية وتسجيل الأخطاء في ملف سجل دون إغلاق نافذة المستخدم.
